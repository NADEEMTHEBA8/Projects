## The Low-Latency ML Feature Dilemma

In real-time fraud detection and decisioning systems, machine learning models need feature inputs (e.g. `count_transactions_1h`, `total_amount_24h`, `velocity_ratio`) calculated over historical windows in under 10 milliseconds. Querying transactional databases like PostgreSQL directly under high concurrency causes extreme query locks and high latencies.

To solve this, we built an event-driven **Streaming Feature Store** architecture combining **Debezium CDC**, **Apache Kafka**, **PySpark Structured Streaming**, and **Redis**.

![Feature Store Architecture](/assets/fraud-cover.png)

## Streaming CDC Pipeline Architecture

1. **Change Data Capture (CDC)**: Debezium captures row updates on PostgreSQL operational tables and publishes change events into Kafka topics.
2. **PySpark Structured Streaming**: PySpark streams consume Kafka topics, apply 1-hour and 24-hour sliding window aggregations, and compute updated customer feature vectors.
3. **Low-Latency Redis Serving**: PySpark writes aggregated feature vectors into Redis key-value stores.
4. **FastAPI Serving Endpoint**: The FastAPI decisioning microservice retrieves feature vectors from Redis in **sub-10ms** latency to score incoming transactions.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import from_json, col, window, count, sum as _sum

spark = SparkSession.builder \
    .appName("RealTimeFraudFeatureStore") \
    .getOrCreate()

# Consume raw transaction stream from Kafka
raw_stream = spark.readStream \
    .format("kafka") \
    .option("kafka.bootstrap.servers", "localhost:9092") \
    .option("subscribe", "postgres.transactions") \
    .load()

# Calculate sliding window aggregations over 1-hour windows
features_df = raw_stream \
    .groupBy(
        window(col("timestamp"), "1 hour", "5 minutes"),
        col("account_id")
    ) \
    .agg(
        count("transaction_id").alias("tx_count_1h"),
        _sum("amount").alias("tx_sum_1h")
    )
```

## Key Achievements

- **Sub-10ms Feature Vector Serving**: Decoupled database read load from inference latency.
- **Exact-Once Processing**: Utilized PySpark streaming checkpointing to guarantee zero duplicate calculations.
- **DLQ Resiliency**: Configured automated Dead-Letter Queue (DLQ) routing to catch malformed event payloads without crashing streaming workers.
